# Bun Mode Manager

`bun run mode:*` 是方便开发者管理项目开发的工具约定。根据具体项目设计命令、运行方式和用法，不把它当作固定框架。一个项目可以只有一种运行方式，也可以有多种；docker、local 只是示例，不强制提供，不为满足命名而引入 Docker 或额外运行环境。

## 控制台格式是硬性要求

命令与模式可以因项目调整，**人类可读输出不能省略**。实施前必须读取 [控制台输出契约](references/console-output.md)，按其状态面板、分组帮助、颜色及验收要求实现。

- `mode:status` 默认必须是有标题、分隔线、对齐字段、分组留白和操作指引的状态面板，禁止默认输出 JSON 或对象。
- `mode:help` 必须按用途分组，以“命令 + 说明”两列对齐，附可复制示例，禁止裸命令列表或密集长段文字。
- 默认输出面向人类；机器输出只通过显式 `--json` 启用。非 TTY/NO_COLOR 仅移除颜色，不能移除排版或自动切换 JSON。
- 终端默认语义化彩色；仅“有 ANSI”并不等于格式合格。中文说明、布局层次与可扫读性也必须验收。

## 实施流程

1. 读取项目规范、package.json、现有运行脚本和实际依赖，了解开发者如何启动、修改、预览和排查项目。修改框架代码前核对该版本的本地文档。
2. 选择能满足项目需求的最小命令集合，复用已有业务脚本。确定是否需要模式选择，以及各命令的目标、行为和参数。保留项目已有的合理约定。
3. 读取 [设计参考](references/design.md)，只采用适用部分。同时完整落实控制台输出契约，不把排版当作可选参考。设计仓库身份、资源隔离；本地 Web 服务尽量默认启用自签 HTTPS。
4. 验证实际命令行为、资源归属、失败处理、访问地址和参数传递；实际预览 status/help 的 TTY、无色和 --json 输出，交付实际输出片段。只修改技能文档时只检查文档，不启动业务服务或迁移数据库。
5. 更新项目运行说明，给出实际实现的命令与预览方法，不列未实现的模式或功能。

## 核心约定

- 命令及语义由项目需求决定。无需机械实现下表全部命令、完整适配器框架或模式切换状态机。
- 如果有多个运行模式，共用的 start/stop/status/logs 等生命周期命令应作用于当前选定模式，明确并保存选择；只有一种方式时可直接使用，无需先选择。
- 模式名称、默认模式、选择后是否启动、reload/restart 的差异，都在项目 help 中明确。没有默认值且选择有歧义时才提示选择，不悄悄操作另一环境。
- 本地 Web 服务尽量默认启用 HTTPS（自签证书或本地 CA 签发）。处理证书、信任与健康探测；项目限制必须使用 HTTP 时说明原因和当前协议，不静默降级。无 Web 服务的项目无需引入 TLS。
- 本地对外 Web 入口支持实际监听 `0.0.0.0`，展示本机及局域网访问 URL；通过 TLS 代理提供入口时，后端可仅绑定回环或容器内部网络。
- 交互终端必须有语义化彩色输出，支持 NO_COLOR/FORCE_COLOR；重定向默认纯文本，机器输出保持可解析。
- 用规范化仓库路径等稳定身份派生端口与资源名称；仅为实际存在的模式、服务增加命名空间。有界处理冲突，停止/清理前校验归属，保护其他项目和持久数据。
- 命令易扩展，复用统一参数传递、日志、退出码和必要的锁。简单项目可以只用薄脚本，复杂项目再引入注册表或适配器。

## 磁盘与缓存生命周期

产生构建缓存、镜像、临时产物或持续日志的项目，必须读取并落实 [磁盘与缓存生命周期](references/storage-lifecycle.md)。采用百分比水位与滞回、最后使用时间过期、按重建成本渐进回收，并在实际构建前和成功更新后接入；缓存预算作为兜底，不使用固定剩余 GB 作为通用触发条件。

- 提供只读清理预览、资源占用与策略展示；持续日志必须轮转。命令名可复用已有约定。
- 自动清理只操作可核验归属的可重建资源，保护业务数据、活动构建及回退版本；禁止无范围全局 prune 或手删 Docker 底层文件。
- 项目级维护不隐含整机清理权限；没有定时触发器时不得宣称长期闲置项目会自行清理。具体默认值、后端能力降级、锁和停止条件见参考。

## 本地配置与运行状态

- 将开发者需要持久保存的选择集中到仓库内一个固定、被 Git 忽略的配置文件，例如 `.local/mode.json`；帮助和状态面板展示实际路径。实例、HTTPS、镜像源或镜像固定等功能存在时，按字段保存，并保留必要的实例 / Docker 环境隔离。
- PID、日志、证书与私钥、构建快照、缓存、锁和生成文件独立存放，不把它们写进配置。环境变量与已有应用配置的覆盖规则明确说明，不为统一入口复制密钥或系统级配置。
- 所有命令通过同一 owner 读写配置，局部更新保留其它字段；并发读改写受锁保护，使用原子替换。损坏配置或不支持的版本应报错，避免静默重置用户选择。
- 合并已有分散配置时，只在新配置不存在时导入，保留原值与资源归属；迁移完成后新文件是唯一读取来源，旧文件仅作备份。测试迁移、重复读取、隔离和并发更新，避免旧文件让已关闭的功能重新开启。

## 可选命令设计参考

下列是语义参考，不是必须实现的接口；最终以项目实际 help 为准。

| 示例 | 可采用的用途 |
| --- | --- |
| `mode:<运行方式>` | 项目需要多模式时选择或切换；名称按项目决定，例如 docker/local |
| `mode:start` / `mode:stop` | 启动/停止当前开发环境 |
| `mode:status` | 展示当前方式、运行状态、真实 URL 及排障信息 |
| `mode:reload` | 一键应用新代码并准备预览；可使用 HMR、增量构建、容器更新或重启 |
| `mode:restart` | 若有单独重启需求则提供，并说明是否重新构建 |
| `mode:build` | 按当前运行方式准备产物，仅在独立构建有用时提供 |
| `mode:logs` / `mode:health` | 日志跟踪和自动化健康检查 |
| `mode:help` | 列出真实可用命令、默认行为与示例 |
| `mode:<自定义任务>` | 接入测试、迁移、生成、诊断等项目任务 |

例如项目采用容器部署预览时，可设计 `mode:reload` 为“利用缓存构建受影响镜像 → 更新必要容器 → 等待健康 → 输出 HTTPS 预览地址”；采用本机 HMR 时则无需每次打包。若 reload 和 restart 在该项目中确实等价，可以复用实现，但必须保证 reload 所承诺的新代码生效行为。

参数使用 argv 数组透传。是否提供 SKIP_BUILD、WAIT_TIMEOUT 等选项也由项目决定；跳过构建不能被描述为已验证新代码生效。
